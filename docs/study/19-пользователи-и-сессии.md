# 19. Web: пользователи, сессии и профиль

> **Из курса** (урок «Авторизация, API и внешние источники», по конспекту `course-map.md`): «Аутентификация отвечает на вопрос „кто ты“, авторизация — „что тебе можно“».

До этого этапа в web был один пользователь — оператор из переменных окружения. Теперь оператор создаёт пользователей, меняет им роль, отключает, сбрасывает пароль и отзывает сессии; каждый пользователь видит свои сессии и меняет пароль сам. Это первый экран web, данные которого лежат не в api, а в собственной базе `web.db`.

## Простыми словами
Сессия — это гардеробный номерок. В браузере лежит номерок (cookie с токеном), в гардеробе — запись «номерок такой-то, пальто такого-то». Отозвать сессию — вычеркнуть запись: номерок на руках остался, но пальто по нему больше не выдадут.

- **Отзыв сессии** — запись `revoked_at` в `web.db`. Токен в cookie после этого бесполезен.
- **Открытый идентификатор сессии** — номер строки в журнале гардероба. По нему запись можно вычеркнуть, но получить пальто нельзя: это не номерок.
- **Последний оператор** — единственный, кто может управлять пользователями. Отключить или понизить его нельзя: вернуть доступ было бы некому.
- **Временный пароль** — пароль, который создал сервер и показал один раз. В базе остаётся только хэш.

## Как это в Nest → как в Next.js
| Задача | Nest | Здесь |
|---|---|---|
| Маршрут с проверкой входа и роли | `@UseGuards(AuthGuard, RolesGuard)` + `@Roles('operator')` | функция `enter(request, services, { role, write, body })` в начале обработчика — [`account-http.ts`](../../apps/web/src/server/account-http.ts) |
| Контроллер | `@Controller('admin/users')` | Route Handler `app/api/admin/users/route.ts` — три строки, логика в `account-http.ts` на стандартных `Request` и `Response` |
| Сервис | `@Injectable() UsersService` | [`UserAdminService`](../../apps/web/src/server/user-admin.ts): зависимости — аргументом конструктора |
| Доменная ошибка → HTTP | `ExceptionFilter` | `fromAdminError`: `UserAdminError.kind` → 400 / 404 / 409 в формате RFC 9457 |
| DTO запроса и ответа | классы с `class-validator`, `@ApiProperty` | общие типы [`lib/account/contract.ts`](../../apps/web/src/lib/account/contract.ts): один файл импортируют сервер и клиент |
| Транзакция | `dataSource.transaction(...)` | [`inTransaction(db, work)`](../../apps/web/src/server/db.ts) — `BEGIN IMMEDIATE` … `COMMIT`, функция `work` синхронная |
| Проверка тела | `ValidationPipe({ whitelist, forbidNonWhitelisted })` | `readObject(request, allowed)`: лишнее поле — 400 |

## В проекте

### Маршруты
Данные живут в `web.db`, поэтому это не прокси в api, а обычные обработчики web.

| Маршрут | Роль | Ответ |
|---|---|---|
| `GET /api/admin/users` | operator | список с числом действующих сессий |
| `POST /api/admin/users` | operator | 201: пользователь и временный пароль |
| `PATCH /api/admin/users/{id}` | operator | пользователь и число отозванных сессий |
| `POST /api/admin/users/{id}/password-reset` | operator | пользователь, временный пароль, число отозванных сессий |
| `GET /api/admin/sessions` | operator | действующие сессии всех пользователей |
| `DELETE /api/admin/sessions/{id}` | operator | 204 |
| `GET /api/me/sessions` | любая | логин, роль, последний вход, свои сессии |
| `DELETE /api/me/sessions/{id}` | любая | 204; для текущей сессии — ещё и стёртая cookie |
| `DELETE /api/me/sessions` | любая | 204, стёртая cookie: «выйти на всех устройствах» |
| `PUT /api/me/password` | любая | 204, стёртая cookie |

Порядок проверок тот же, что у BFF: **401 → 403 (роль) → 415 → 403 (чужой сайт) → 400**. Без сессии нельзя узнать даже то, что маршрут существует.

### Контракт — общие типы, а не вторая спека
У api контракт — OpenAPI: его читают сторонние клиенты, по нему строится роутер и Swagger. У `/api/admin/*` потребитель один — сам web. Поэтому контракт — файл типов [`contract.ts`](../../apps/web/src/lib/account/contract.ts): обработчик собирает ответ со `satisfies UserList`, клиент возвращает `Promise<UserList>`. Разойтись им не даёт компилятор.

Константы (формат логина, длина пароля) в этом файле повторяют серверные — `passwords.ts` нельзя импортировать в браузер. Совпадение проверяет [тест](../../apps/web/tests/account-http.test.ts).

Клиент — [`createAccountClient`](../../apps/web/src/lib/account/client.ts). Разбор ответов общий с клиентом BFF: из `bff-client.ts` вынесена функция `createJsonRequest` (JSON, 204, ошибка RFC 9457, 401 → страница входа).

### Открытый идентификатор сессии
Первичный ключ таблицы `sessions` — SHA-256 токена. Отдавать его в браузер как идентификатор нельзя: это проверочное значение, и чем меньше мест, где оно появляется, тем лучше. Миграция [`0002`](../../docs/project/schema/web_0002_session_id.sql) добавляет колонку `public_id` — 16 случайных байт, с токеном никак не связанных:

```sql
ALTER TABLE sessions ADD COLUMN public_id TEXT CHECK (length(public_id) = 32 AND …);
UPDATE sessions SET public_id = lower(hex(randomblob(16)));   -- сессии, созданные до миграции
CREATE UNIQUE INDEX sessions_public_id ON sessions (public_id);
```

`ALTER TABLE … ADD COLUMN` в SQLite не умеет `NOT NULL` без значения по умолчанию и `UNIQUE`, поэтому шага три. В ответах API хэша токена нет: по нему сервер только помечает текущую сессию (`isCurrent`).

### Последний оператор
[`UserAdminService.update`](../../apps/web/src/server/user-admin.ts) проверяет: если пользователь был активным оператором и перестаёт им быть, а активных операторов не больше одного — отказ 409 `last-operator`.

Проверка и запись идут в одной транзакции. Гонка «два оператора одновременно понижают друг друга» здесь невозможна и без неё: `node:sqlite` синхронный, между проверкой и записью нет `await`, значит Event Loop не может вклинить второй запрос. Транзакция нужна для другого: смена роли и отзыв сессий либо происходят вместе, либо не происходят.

Экран повторяет правило подсказкой ([`lockReason`](../../apps/web/src/lib/account/forms.ts)): кнопки неактивны и объясняют причину. Решение всё равно принимает сервер.

### Что отзывает сессии
| Действие | Причина в `revoke_reason` | Почему |
|---|---|---|
| Смена роли | `admin` | открытые вкладки нарисованы под прежнюю роль |
| Отключение | `user_disabled` | — |
| Сброс пароля оператором | `password_changed` | прежний пароль мог быть украден вместе с сессией |
| Смена своего пароля | `password_changed` | то же; текущая сессия тоже отзывается |
| «Отозвать» у оператора | `admin` | — |
| «Завершить» в профиле | `logout` | — |
| «Выйти на всех устройствах» | `logout_all` | — |

Включение пользователя сессий не возвращает: отзыв необратим.

### Временный пароль
Пароль создаёт сервер — [`generatePassword`](../../apps/web/src/server/user-admin.ts): 15 случайных байт в base64url, 20 символов, 120 бит. Оператор не может выбрать слабый пароль и не знает постоянного. Пароль возвращается в теле ответа один раз, в базу попадает хэш scrypt, в лог — только факт сброса.

Свой пароль оператор так не сбрасывает (409 `own-password-reset`): ответ с новым паролем пришёл бы в сессию, которую этот же запрос отозвал.

Ограничение: смена временного пароля при первом входе не принудительная. Пользователь меняет его сам в профиле.

### Смена своего пароля
[`changeOwnPassword`](../../apps/web/src/server/user-admin.ts) требует текущий пароль: украденной сессии для смены недостаточно. Перебор текущего пароля через этот маршрут упирается в ту же прогрессивную задержку, что и вход (общий ключ — логин и адрес): пять попыток без ожидания, дальше 429 с `Retry-After`. Во время ожидания scrypt не считается.

### Отзыв закрывает поток событий
Открытое SSE-соединение само не закроется: запрос уже прошёл проверку. Поэтому прокси `/api/stream` перепроверяет сессию на каждом heartbeat api (25 с) — это сделано в C2. Здесь проверено на практике, на стенде в Docker: оператор отозвал сессию пользователя с открытым потоком, обычный запрос этой сессии сразу получил 401, а поток получил событие `session.expired` и закрылся **через 25,0 с** — худший случай, heartbeat прошёл прямо перед отзывом. Переподключение — 401.

### Кэш без событий потока
По пользователям и сессиям событий нет: поток идёт из api, а эти данные — в `web.db`. Правило «кэш из ответа мутации» ([разбор 18](18-панель-оператора-и-мутации.md)) работает так:

| Мутация | В ответе | Что делает экран |
|---|---|---|
| Создание, роль, статус, сброс | пользователь, число отозванных сессий | пользователь — в кэш; список сессий перечитывается, только если сессии отозваны |
| Отзыв сессии | 204 | строка убирается из кэша; счётчики пользователей перечитываются |
| Отказ (404, 409) | Problem | перечитывается всё показанное: экран устарел |

Код — [`lib/account/queries.ts`](../../apps/web/src/lib/account/queries.ts).

### Действие над собой
Оператор, понизивший или отключивший себя (когда есть другой оператор), теряет сессию тем же запросом. Диалог предупреждает об этом, а экран после ответа сразу ведёт на вход — не дожидаясь, пока следующий запрос получит 401.

## Подводные камни
- **`instanceof` для доменной ошибки не сработал на собранном образе.** Занятый логин давал 500 вместо 409, хотя тесты проходили. Причина: сервисы создаются один раз на процесс и лежат в `globalThis`, а сборка Next положила модуль `user-admin.ts` в два чанка — у каждого свой экземпляр класса `UserAdminError`. Ошибку бросил экземпляр из одного чанка, а `instanceof` проверял класс из другого. В Jest модуль один, поэтому тест этого не видел. Исправление — проверка по имени и полю ([`isUserAdminError`](../../apps/web/src/server/user-admin.ts)) и тест с «чужим» классом. Найдено только проверкой в браузере на Docker-стенде.
- **`ALTER TABLE ADD COLUMN` в SQLite ограничен**: без `UNIQUE` и без `NOT NULL` для существующих строк. Уникальность — отдельным индексом, заполнение — отдельным `UPDATE`.
- **Число точек истории в диалоге удаления получено без изменения api.** Первое решение — поле в `getCryptocurrency` — нарушало бы правило брифа «контракт ТЗ-эндпоинтов не меняется». То же число уже отдаёт сводка `getPriceAggregates` (`summary.points`) — [ADR 0017, пробел 3](../adr/0017-web-ui-data-gaps.md).
- **`void` как аргумент дженерика запрещён линтером** (`no-invalid-void-type`): `request<undefined>` вместо `request<void>`.
- **Временный пароль живёт только в состоянии экрана.** Закрыли диалог — увидеть его нельзя, только сбросить заново. Диалог не закрывается кликом мимо.
- **Экрана пользователей нет в макетах.** Вёрстка собрана из тех же блоков, что watchlist: таблица на широком экране, карточки на узком.
- **Без доверенного прокси IP сессии неизвестен** (`WEB_TRUST_PROXY=false`): в колонке «IP» — прочерк.

## Вопросы на собеседовании
1. **Оператор отозвал сессию. Когда пользователь реально теряет доступ?** → Обычные запросы — сразу: сессия проверяется в БД на каждом запросе. Открытый поток событий — до 25 секунд: прокси перепроверяет сессию на heartbeat. С JWT без списка отзыва доступ остался бы до истечения токена.
2. **Почему идентификатор сессии в API — не хэш токена?** → Хэш — проверочное значение: по нему сервер узнаёт токен. Открытый идентификатор — отдельное случайное число: зная его, сессию можно отозвать (и то лишь имея на это право), но нельзя ею воспользоваться.
3. **Как защищено правило «последний оператор» от гонки двух запросов?** → Проверка и запись идут синхронно, без `await` между ними: Node выполняет их как один кусок, второй запрос не вклинится. При нескольких процессах или асинхронном драйвере понадобилась бы транзакция с блокировкой — `BEGIN IMMEDIATE` здесь уже стоит.
4. **Почему `instanceof` может вернуть `false` для «своего» класса?** → Класс — это объект, созданный при выполнении модуля. Если модуль выполнен дважды (два чанка сборки, две копии пакета в `node_modules`, два realm), классов два. Надёжнее проверять по признаку: имя, поле-дискриминант, `Symbol.for`.
5. **Почему пароль создаёт сервер, а не оператор?** → Оператор не выбирает слабый пароль и не знает постоянного; пароль показан один раз и нигде не хранится. Цена — нет принудительной смены при первом входе: это записано как ограничение.
6. **Зачем текущий пароль при смене, если пользователь уже вошёл?** → Сессия и пароль — разные секреты. Украденная cookie без пароля не должна давать постоянный доступ к учётной записи. По той же причине после смены отзываются все сессии.
