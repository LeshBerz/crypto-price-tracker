# 18. Web: панель оператора, мутации и расписание синхронизации

> **Из курса** (урок «Авторизация, API и внешние источники», по конспекту `course-map.md`): «REST: ресурсы-URL + HTTP-методы + статус-коды, stateless».

Панель оператора — первый экран web, который не только читает, но и пишет. Здесь статус-код перестаёт быть деталью протокола: 201, 202, 204, 400, 409, 422 и 503 — семь разных исходов одной кнопки, и у каждого своё поведение интерфейса.

## Простыми словами
Чтение — это взгляд на витрину: можно смотреть сколько угодно, витрина не меняется. Запись — это заказ у продавца. Заказ принят (201), принят и собирается (202), такой товар уже лежит в корзине (409), такого товара не бывает (422), склад закрыт, зайдите через полминуты (503). Продавец не говорит «готово», пока товар не выдан, — и интерфейс не рисует результат, пока api его не подтвердил.

- **Мутация** — запрос, который меняет данные: `POST`, `PATCH`, `DELETE`.
- **Обновление из ответа** — api возвращает сохранённый объект, он и кладётся в кэш. Это не оптимистичное обновление: до ответа экран не меняется.
- **202 Accepted** — «принято, работа идёт». Итог придёт позже, событием `sync.finished`.
- **Определение возможности по ответу** — интерфейс показывает расписание, только если api его отдал.

## Как это в Nest → как в Next.js и React
| Задача | Nest (сервер) | Здесь (браузер + BFF) |
|---|---|---|
| Доступ по роли | `@Roles('operator')` + `RolesGuard` | [`operator/layout.tsx`](<../../apps/web/src/app/(app)/operator/layout.tsx>) (разметка) и allowlist BFF (данные) — две проверки на сервере |
| Проверка тела запроса | `ValidationPipe` + DTO → 400 | [`parseAddForm`](../../apps/web/src/lib/operator/watchlist.ts): та же проверка до запроса; api проверяет снова |
| Ошибка → ответ | `ExceptionFilter` → Problem Details | [`describeAddFailure`](../../apps/web/src/lib/operator/watchlist.ts): Problem → сообщение у поля или в форме |
| Долгая операция | `@HttpCode(202)` + очередь | `useMutation` кладёт запуск `running` в кэш, итог приносит событие |
| Защита записи от CSRF | `csurf` или SameSite-cookie | `Content-Type: application/json` + проверка `Origin` в BFF ([ADR 0016](../adr/0016-web-auth-and-bff-routes.md)) |
| Необязательное поле в ответе | версия DTO, `@ApiPropertyOptional` | [`readSchedule`](../../apps/web/src/lib/operator/system.ts): поле проверяется по форме, нет поля — нет блока на экране |

## В проекте

### Клиент BFF: запись на типах контракта
[`bff-client.ts`](../../apps/web/src/lib/bff-client.ts) получил метод `send(method, path, options)`. Путь, тело и ответ выводятся из сгенерированного `paths`:

```ts
bff.send('patch', '/api/v1/cryptocurrencies/{id}', { params: { id }, body: { isPaused: true } });
//        ↑ метод, которого у пути нет, — ошибка компиляции
//                                                    ↑ params обязателен: в пути есть {id}
//                                                                    ↑ body — UpdateCryptocurrencyRequest
```

- У операции без тела (`POST /sync-runs`, `DELETE`) поле `body` запрещено типом.
- `Content-Type: application/json` ставится у `POST` и `PATCH` **даже без тела**. Это слой защиты от CSRF: HTML-форма с чужого сайта такой заголовок отправить не может, а BFF без него отвечает 415.
- Ответ 204 возвращается как `undefined`.
- `BffError` несёт `retryAfterSeconds` (заголовок `Retry-After`) и `body` — JSON, который не является Problem.
- Признака фона у записи нет: за ней всегда действие пользователя, сессия продлевается.

### Мутация → кэш: из ответа, а не по событию
Решение этапа: после успешного ответа кэш правится из тела ответа ([`applyCoinSaved`](../../apps/web/src/lib/operator/watchlist.ts), `applyCoinDeleted`, [`upsertRun`](../../apps/web/src/lib/operator/queries.ts)).

| Вариант | Что на экране при отключённом потоке | Откат при отказе |
|---|---|---|
| Ждать `watchlist.changed` | Ничего не меняется до переподключения | не нужен |
| Оптимистично до ответа | Меняется сразу | нужен; для добавления ответ непредсказуем (имя, CMC ID, 409, 422, 503) |
| **Из ответа api** | Меняется после ответа | не нужен: в кэше только подтверждённое |

Событие `watchlist.changed` остаётся — оно обновляет другие вкладки и других пользователей. В своей вкладке оно придёт следом и вызовет фоновый перезапрос списка: один лишний GET на мутацию. Это цена простоты: отличать «своё» событие от «чужого» не нужно.

Чего в ответе мутации нет (цены, мини-графики) — помечается устаревшим (`invalidateQueries`). Запрос уйдёт, только если эти данные сейчас на экране.

### Список монет: один ключ на два экрана
Watchlist оператора и дашборд читают один запрос `['cryptocurrencies']`. Время последней цены в таблице оператора обновляет `price.updated` — [`applyToCoinList`](../../apps/web/src/lib/dashboard/stream-events.ts) правит строку на месте. Перечитывать список после каждой синхронизации не нужно: состав и паузу меняет только `watchlist.changed`.

### Семь исходов добавления монеты
[`describeAddFailure`](../../apps/web/src/lib/operator/watchlist.ts) превращает отказ api в данные для формы. Интерфейс смотрит на `type` из Problem (стабильный URN), а не на текст.

| Ответ | Где сообщение | Что ещё |
|---|---|---|
| 201 | уведомление «Добавлен Bitcoin (CMC #1)» | видно, какую монету выбрал сервис: символы в CoinMarketCap не уникальны |
| 400 | у поля — по `errors[].path` (`/body/symbol`, `/body/cmcId`) | ошибка не про поля формы → общее сообщение |
| 409 `already-tracked` | у символа | ссылка на карточку по `conflictingId` |
| 422 `unknown-symbol` | у символа | подсказка зависит от того, был ли указан CMC ID |
| 422 `watchlist-limit-reached` | предупреждение формы | |
| 503 | ошибка формы | кнопка неактивна, отсчёт по `Retry-After` |
| 502 / 504 от BFF, нет сети | ошибка формы | отсчёта нет: api не сказал, сколько ждать |

### Ручной запуск: 202 и событие
[`sync-panel.tsx`](../../apps/web/src/components/operator/sync-panel.tsx): `POST /sync-runs` → 202 → запуск со статусом `running` попадает в журнал из ответа. Итог приносит `sync.finished`: правило в `parseStreamEvent` добавляет цели `syncRuns`, `cmc`, `readiness`, и `refreshInBackground` перечитывает первую страницу журнала фоновым запросом. Опроса по таймеру нет.

- 409 `sync-already-running` → уведомление, журнал перечитывается, строка с `conflictingId` подсвечивается.
- Поток отключён → экран говорит об этом прямо и предлагает кнопку «Обновить». Экран читает только **состояние** потока из контекста; на события он не подписан.

### Готовность: 503 — это данные
`/health/ready` отвечает 503 с тем же JSON, что и 200. Для экрана «Система» это не ошибка запроса, а ответ «не готов, и вот почему». [`readinessQuery`](../../apps/web/src/lib/operator/queries.ts) возвращает такое тело как данные (форма проверяется `isReadiness`). Ошибкой остаётся только отсутствие ответа api.

### Расписание: интерфейс для двух версий api
Блок `schedule` в `getCmcStatus` — контракт `1.1.0` (ветка `feat/api-sync-schedule`, [ADR 0017](../adr/0017-web-ui-data-gaps.md)). В `main` api — `1.0.0`, блока нет.

[`readSchedule`](../../apps/web/src/lib/operator/system.ts) читает блок из ответа и проверяет форму. Нет блока — `null`: «Следующий запуск», «Расписание» и прогноз квоты на экране не появляются. После вливания ветки они появятся без изменения кода web.

На стороне api ([`scheduler.ts`](../../apps/api/src/sync/scheduler.ts), ветка): `nextRunAt` выставляется перед ожиданием и сбрасывается в `null` перед запуском. Планировщик отсчитывает интервал от **завершения** запуска, поэтому во время запуска время следующего неизвестно — и api честно отдаёт `null`.

### Прогноз квоты
[`forecastQuota`](../../apps/web/src/lib/operator/system.ts): `кредитов на запуск × запусков до конца месяца`. Средний расход — по последним 20 запускам с известным `creditsUsed`. Оценка намеренно сверху: запуски считаются каждые `intervalMs`, хотя на деле их чуть меньше. Прогноз скорее предупредит зря, чем промолчит.

### Удаление: подтверждение вводом символа
[`DeleteDialog`](../../apps/web/src/components/operator/coin-dialogs.tsx): удаление стирает историю цен и свёртки ([ADR 0013](../adr/0013-data-model.md)), поэтому кнопка активна только после ввода символа. Рядом — «Поставить на паузу»: действие, которое историю сохраняет. Диалог монтируется с `key={coin.id}`: состояние поля живёт, пока открыт диалог одной монеты, и не сбрасывается эффектом.

### Диалог и уведомления без новых зависимостей
[`ui/dialog.tsx`](../../apps/web/src/components/ui/dialog.tsx) и [`ui/toast.tsx`](../../apps/web/src/components/ui/toast.tsx) — обёртки над `@base-ui/react`, который уже установлен. Очередь уведомлений создаётся вне дерева React (`createToastManager`): её вызывают обработчики мутаций, а показывает `Toaster` в layout. Ошибка объявляется скринридеру сразу (`priority: 'high'`), остальное — когда он договорит.

## Подводные камни
- **Число точек в диалоге удаления получено без нового поля в api.** В макете — «будет удалена вся история BTC — 12 480 точек», а `Cryptocurrency` числа точек не отдаёт. Поле в ТЗ-эндпоинте нарушило бы правило брифа; то же число уже есть в сводке `getPriceAggregates` (`summary.points`) — один запрос на открытие диалога ([ADR 0017, пробел 3](../adr/0017-web-ui-data-gaps.md)). Пока запрос идёт или не удался, диалог говорит «вся история цен» без числа.
- **Страница «Недостаточно прав» отвечает HTTP 200.** `forbidden()` в Next.js 16 требует экспериментального флага. Данные защищены: BFF отвечает 403 на каждый запрос оператора от Viewer.
- **Prettier из каталога `apps/web` не видит корневой `.prettierignore`** и переформатирует сгенерированные типы. Форматирование — из корня репозитория.
- **`POST` без тела и без `Content-Type` — 415 от BFF.** Заголовок ставится всегда, а не «когда есть тело».
- **После перезапуска api квота `null`**: кэш `key/info` хранится в памяти процесса. Экран показывает «квота ещё не получена» до первой синхронизации.
- **Два набора кнопок в DOM.** Таблица и карточки для телефона отрисованы обе, одну скрывает CSS (`display: none` — из дерева доступности она тоже исчезает). Так же устроен дашборд.
- **Своё событие `watchlist.changed` даёт лишний GET** после мутации. Осознанно: см. «Мутация → кэш».
- **Шапка на 375 px перестала помещаться** после появления пункта «Оператор»: горизонтальная прокрутка страницы. Роль перенесена в меню пользователя на узком экране. Найдено проверкой `scrollWidth` в браузере.

## Вопросы на собеседовании
1. **Почему после мутации кэш обновляется из ответа, а не по событию потока и не оптимистично?** → Событие может не прийти: поток отключён. Оптимистичное обновление требует отката, а результат добавления непредсказуем (имя и CMC ID выбирает сервис, возможны 409, 422, 503). Из ответа в кэш попадает только подтверждённое.
2. **Чем 202 отличается от 201 и что делает клиент после 202?** → 201 — ресурс создан и готов. 202 — запрос принят, работа идёт. Клиент показывает запуск `running` и ждёт события `sync.finished`; опроса нет, при отключённом потоке — кнопка «Обновить».
3. **Зачем `Content-Type: application/json` у POST без тела?** → Это защита от CSRF: «простой» запрос из HTML-формы чужого сайта такой заголовок нести не может, а запрос с ним требует preflight, который BFF не разрешает. Плюс проверка `Origin`.
4. **Как web работает с двумя версиями api?** → Определением возможности по ответу: блок `schedule` читается и проверяется по форме; нет блока — элементы интерфейса не показываются. Обратная совместимость держится на том, что поле добавлено, а не изменено.
5. **Почему `/health/ready` с 503 — не ошибка для экрана?** → Тело 503 — тот же состав проверок. Это ответ на вопрос «готов ли сервис», и ответ «нет, миграции не применены» — полезные данные. Ошибка — когда ответа нет.
6. **Где проверяется, что пользователь — оператор?** → На сервере дважды: layout не отдаёт разметку, BFF не отдаёт данные (allowlist: операция → минимальная роль). Третий слой — api: у ключа viewer нет нужных scope. Скрытый пункт меню защитой не является.
