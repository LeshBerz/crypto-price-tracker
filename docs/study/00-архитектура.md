# 00. Архитектура: порты и адаптеры, spec-first, события после COMMIT

> **Из курса** (урок «Структура и архитектура Node.js-приложений»): «Эти слои образуют вертикальную архитектуру, где зависимость направлена внутрь — от внешних интерфейсов (HTTP, CLI) к ядру бизнес-логики. Внешние слои могут зависеть от внутренних, но не наоборот».

## Простыми словами

У сервиса есть **ядро** — бизнес-правила: добавить монету, синхронизировать цены, посчитать агрегаты. Ядру всё равно, откуда пришёл вызов (HTTP, таймер, CLI) и где лежат данные (SQLite, Postgres). Оно описывает, что ему нужно, интерфейсами — **портами**: «дай репозиторий цен», «дай котировки», «опубликуй событие», «скажи, который час». Конкретные реализации — **адаптеры** — подставляются снаружи, в одном месте, которое называется **composition root**.

Аналогия — розетка и вилка. Ядро — прибор с вилкой стандартной формы (порт). Неважно, от какой станции идёт ток (адаптер): прибор работает одинаково. Поменять станцию можно, не разбирая прибор.

Ещё два решения держат конструкцию:
- **Spec-first.** `openapi.yaml` написан до кода и управляет маршрутами, валидацией, типами и Swagger. Эндпоинта «мимо спеки» не существует.
- **События после COMMIT.** Сначала данные надёжно в БД, потом уведомление. Иначе при откате транзакции клиент увидит цену, которой нет.

## Как это в Nest → как в Express

| Nest | У нас (Express, без DI-контейнера) |
|---|---|
| `@Module` с `providers` | composition root `apps/api/src/server.ts`: создаёт адаптеры и передаёт их в `createApp(deps)` |
| `{ provide: PRICE_REPO, useClass: SqlitePriceRepo }` | `const prices = new SqlitePriceRepository(db)` → аргумент сервиса |
| `@Injectable()` сервис с `constructor(@Inject(PRICE_REPO) repo)` | сервис принимает порт-интерфейс в конструкторе или фабрике |
| Подмена в тестах: `Test.createTestingModule().overrideProvider()` | в тестах `createApp({ clock: new FakeClock(), market: stubCmc, … })` |
| `@Controller` + `@Get` + `ValidationPipe` + `@UseGuards` | роутер из спеки: по `operationId` монтирует auth → валидацию → хендлер |
| `@nestjs/swagger` генерирует спеку из кода (code-first) | спека пишется руками, код подчиняется ей (spec-first) |
| `EventEmitter2` / `@nestjs/cqrs` EventBus | порт `EventBus`, адаптер in-process; в `platform` — Redis + RabbitMQ |

Почему без DI-контейнера: десяток зависимостей, явная передача читается сверху вниз и отлаживается без магии рефлексии. Контейнер окупается на сотнях провайдеров.

## Подводные камни

- **Порт по форме библиотеки.** Если `MarketDataProvider.getQuotes` вернёт сырой ответ CMC, ядро начнёт зависеть от формата CMC — порт протёк. Порт описывает потребность ядра (`Quote { cmcId, price: string, sourceUpdatedAt }`), маппинг живёт в адаптере.
- **Синхронный порт.** `node:sqlite` синхронный, и хочется сделать репозитории синхронными. Тогда Postgres-адаптер не встанет на место. Интерфейсы — `Promise`, даже если реализация синхронна.
- **Время в обход порта.** `Date.now()` или `setTimeout` из `node:timers/promises` прямо в сервисе ломают детерминизм тестов: fake timers Jest не подменяют `node:timers/promises` (проверено, ADR 0009). Время — только через `Clock`, ESLint это запрещает.
- **Публикация внутри транзакции.** Событие ушло, транзакция откатилась — у клиента «фантомная» цена. Публикуем только после COMMIT.
- **Phantom dependency.** npm поднимает зависимости в корень, и `apps/api` может случайно импортировать `ioredis` соседнего пакета. Ловит `scripts/check-deps.ts` (ADR 0004, 0005).

## Вопросы на собеседовании

1. Что такое порт и адаптер, и чем это отличается от «слоёной» архитектуры controller → service → repository? → Слои — про направление вызовов; порты — про направление **зависимостей**: ядро владеет интерфейсами, инфраструктура их реализует (DIP). Поэтому ядро можно собрать с другими адаптерами без правок.
2. Почему события публикуются только после COMMIT и что теряется при падении процесса между коммитом и публикацией? → Иначе при откате клиент увидит несуществующие данные. Теряется только уведомление (at-most-once), данные в БД; клиент перечитывает состояние по REST.
3. Spec-first или code-first — что выбрал и почему? → Spec-first: контракт готов до кода (API-first), дрейф исключён, потому что валидатор и роутер читают ту же спеку.
4. Зачем composition root без DI-контейнера? → Явные зависимости при малом их числе проще читать и тестировать.
5. Как ты гарантируешь, что в рантайм `apps/api` не попала запрещённая библиотека? → `check-deps` в CI и pre-commit + прод-образ через `npm ci --omit=dev`.
