# 0007. Агрегаты: на лету или хранимые свёртки

- **Статус:** Accepted (06.10.2026)
- **Дата:** 06.10.2026
- **Вопрос брифа:** Q5
- **Требования:** ТЗ «отслеживание и **агрегация** цен», F4, F5, C2; бриф §3 «История и агрегаты»
- **Связано:** [0003 — синхронный `node:sqlite`](0003-sqlite-driver-and-node-version.md), [0006 — точность цен](0006-price-precision.md)

## Контекст

Что нужно отдавать (бриф): историю за период, бакеты по интервалам (1h / 1d …) с open / close / min / max / avg и % изменения.

### Входные данные

| Параметр | Значение | Откуда |
|---|---|---|
| План CMC Basic | 15 000 кредитов/мес, 50 запросов/мин, данные обновляются раз в 60 с, **исторических эндпоинтов нет** | [CMC Pricing](https://coinmarketcap.com/api/pricing/) |
| Интервал синхронизации по умолчанию | **5 минут**: 8 640 вызовов/мес ≤ 15 000, остаётся запас на ручной запуск и проверку символов. Минимум при 1 кредите на вызов — ~2,9 мин | расчёт; детали — в ADR планировщика |
| Объём | 288 точек/сутки на монету → ~105 тыс./год. 20 монет → **2,1 млн строк/год, ~147 МБ** | замер |
| Историю из CMC не догрузить | всю историю копим сами, и агрегаты строятся только по ней | план Basic |

**Ключевое ограничение — синхронный драйвер (ADR 0003).** Пока выполняется SQL, Event Loop стоит, и **все** запросы, включая `/status`, ждут. Значит, считаем не «среднее время ответа», а бюджет блокировки: **≤ ~20 мс** на запрос.

### Замеры (Node 24.21, SQLite 3.53, 2,1 млн строк, индекс `(coin, fetched_at)`)

| Запрос | На лету по сырым данным | Через часовые свёртки |
|---|---|---|
| Сырые точки за 24 ч (288 шт.) | **0,2 мс** | — |
| 7 дней по 1 ч (168 бакетов) | **2,8 мс** | — |
| 30 дней по 1 ч (720 бакетов) | **12,8 мс** | (это и есть свёртки — чтение 720 строк) |
| 1 год по 1 дню (365 бакетов) | ❌ **178,8 мс** | ✅ **10,4 мс** (SQL по 8 760 строкам свёрток) |
| Точный avg на BigInt за год по сырым (105 тыс. строк) | ❌ 145 мс | 38,8 мс (BigInt по свёрткам в приложении) |
| Построение свёрток с нуля для 20 монет × год | — | 6,7 с (разово, при миграции или восстановлении) |

### Подводные камни, найденные при замерах

1. **`node:sqlite` передаёт JS `number` как REAL.** `SELECT typeof(:p)` для `2` даёт `real`, а `7 / :p` — `3.5`. Бакетизация `fetched_at / :size` молча становится дробной: каждая строка попадает в свой «бакет». Целочисленные параметры **обязательно** передаём как `BigInt` (`2n` → `integer`, `7 / 2n` = `3`). Правило для всех репозиториев, проверяется тестом.
2. **Эпоха Unix началась в четверг.** Наивный `floor(t / 7 дней)` даёт недели «с четверга». Недельные бакеты выравниваем по понедельнику (ISO 8601).
3. **Exact min/max без float в ответе.** В SQLite есть «bare columns»: `SELECT price, MAX(price_num) … GROUP BY bucket` возвращает `price` той самой строки, где достигнут максимум. Так ADR 0006 соблюдается и в агрегатах: наружу уходит точный TEXT наблюдённой цены.

## Варианты

1. **На лету по сырым данным** — `GROUP BY` при каждом запросе.
2. **Хранимые свёртки всех уровней** (1h, 1d, 1w …) — отдельные таблицы, обновляются при синхронизации.
3. **Гибрид: сырые данные + одна часовая свёртка.** Мелкие интервалы и короткие периоды — из сырых, крупные — пересчётом часовых свёрток на лету.
4. **Агрегация в приложении** — читаем сырые строки и считаем в JS.

## Сравнение

| Критерий | 1. На лету | 2. Все уровни | 3. Гибрид raw + 1h | 4. В приложении |
|---|---|---|---|---|
| Год по дням в бюджете ~20 мс | ❌ 179 мс | ✅ | ✅ 10 мс | ❌ 145 мс+ |
| Время растёт с… | числом сырых строк в периоде | числом бакетов | числом часов в периоде (в 12 раз меньше сырых) | числом сырых строк |
| Объём кода | ✅ минимум | ❌ N таблиц, N пересчётов | 🟡 одна таблица и один upsert | 🟡 |
| Риск рассинхрона | ✅ нет | ❌ на каждом уровне | 🟡 один уровень, пересчёт идемпотентен и в той же транзакции | ✅ нет |
| Гибкость интервалов | ✅ любые | ❌ только хранимые | ✅ любые, кратные часу | ✅ |
| Нормальная практика? | ✅ для малых объёмов | ✅ OLAP | ✅ так устроены continuous aggregates в TimescaleDB | — |

## Решение (рекомендация)

**Вариант 3: сырые данные + часовая свёртка `price_rollups_1h`, которая пересчитывается в той же транзакции, что и вставка цен.**

### Хранение

```sql
-- время везде: INTEGER, Unix epoch в миллисекундах, UTC
CREATE TABLE price_rollups_1h (
  cryptocurrency_id INTEGER NOT NULL REFERENCES cryptocurrencies(id) ON DELETE CASCADE,
  bucket_start      INTEGER NOT NULL,          -- начало часа, UTC, мс
  points            INTEGER NOT NULL CHECK (points > 0),
  open              TEXT    NOT NULL,          -- точные цены наблюдённых точек (ADR 0006)
  close             TEXT    NOT NULL,
  min               TEXT    NOT NULL,
  max               TEXT    NOT NULL,
  min_num           REAL    GENERATED ALWAYS AS (CAST(min AS REAL)) VIRTUAL,
  max_num           REAL    GENERATED ALWAYS AS (CAST(max AS REAL)) VIRTUAL,
  sum_num           REAL    NOT NULL,          -- для avg (см. ниже)
  PRIMARY KEY (cryptocurrency_id, bucket_start)
) WITHOUT ROWID;
```

- **Пересчёт.** После вставки цен синхронизация в **той же транзакции** выполняет `INSERT … SELECT … FROM price_history WHERE coin = ? AND fetched_at` в пределах текущего часа `ON CONFLICT DO UPDATE`. Пересчёт **идемпотентный**: свёртка всегда целиком пересобирается из сырых строк своего часа, а не накапливается через `+=`. Повтор синхронизации или ретрай не исказит данные.
- **Восстановление.** Команда `npm run rollups:rebuild` пересобирает свёртки из `price_history`. Сырые данные — источник истины, свёртка — производный кэш.
- **Ничего не удаляем.** Сырые данные храним бессрочно: ТЗ требует историю. Retention — возможность на будущее, а не часть этой работы.

### Чтение: какой источник для какого интервала

| `interval` | Источник | Ограничение |
|---|---|---|
| `raw` (точки как есть) | `price_history` | пагинация, `limit ≤ 1000` |
| `1h` | `price_rollups_1h` напрямую | бакетов в ответе ≤ 1000 |
| `4h`, `1d`, `1w` | `price_rollups_1h` → `GROUP BY` на лету (bare columns) | бакетов в ответе ≤ 1000 |

Правило лимита одно: `(to − from) / interval ≤ 1000`, иначе **400** с понятным сообщением. Это валидация входа (C10) и защита Event Loop одновременно.

### Семантика полей бакета

| Поле | Что это | Точность |
|---|---|---|
| `bucketStart` | начало бакета, ISO 8601 UTC. Недели — с понедельника | — |
| `open` / `close` | первая и последняя наблюдённые цены | точно (TEXT) |
| `min` / `max` | экстремумы — реальные наблюдённые цены | точно (TEXT, bare columns) |
| `avg` | среднее по точкам | **статистика**: считается в double, отдаётся строкой, округлённой до 10 значащих цифр (HALF_EVEN) |
| `changePercent` | `(close − open) / open × 100` | точно в `Decimal`, 4 знака после запятой, HALF_EVEN |
| `points` | сколько точек в бакете | — |

- **Пропуски** (CMC лежал, сервис был выключен): пустые бакеты **не выдумываем** и не интерполируем, их просто нет в ответе. `points` показывает, насколько бакет полон.
- **Изменение за 24 ч** для актуальных цен: последняя цена против последней точки не позже `now − 24h`. Если истории меньше суток — `null` (а не 0 и не ошибка).

### Почему avg во float, если ADR 0006 против float

- **Среднее — это не цена, а статистика.** Ни одной сделки по нему не было, денег за ним нет.
- **Погрешность double ничтожна.** Относительная ошибка ~1e-16 на операцию, на 1e5 сложений — не больше ~1e-11. Это на порядки меньше округления до 10 значащих цифр, так что ответ совпадает с точным расчётом.
- **Точный расчёт стоит в 4 раза дороже.** BigInt-вариант — 39 мс против 10 мс при синхронном драйвере, который блокирует все запросы.
- **Альтернатива на будущее.** Хранить точную сумму TEXT в свёртке и суммировать в `Decimal` (39 мс). Включается без изменения контракта.

## Последствия

- ➕ Любой период ≤ 1000 бакетов отвечает за ≤ ~13 мс и не растёт с возрастом данных: часов в 12 раз меньше, чем сырых точек.
- ➕ Агрегаты честные: экстремумы и open/close — реальные цены. Пропуски видны, а не замазаны.
- ➕ Сильные интервью-темы: бюджет блокировки Event Loop при синхронном драйвере, идемпотентный пересчёт, bare columns, `number` → REAL в биндингах, неделя «с четверга».
- ➖ Вторая таблица и пересчёт внутри синхронизации. Покрываем тестами: пересчёт после вставки, повторный запуск, rebuild совпадает с инкрементом.
- ➖ Интервалы мельче часа (кроме `raw`) не поддерживаются. Для дашборда это не нужно.
- **Время храним как INTEGER epoch ms UTC, в API — ISO 8601 UTC.** Дешёвая арифметика бакетов и сортировка без парсинга строк. Курс допускает и ISO-строку, и Unix time. Перенести в ADR модели данных.
- `platform` (Q8): свёртку заменяет continuous aggregate TimescaleDB, а контракт API не меняется.

## Как защищать на интервью

«Агрегирую гибридно. Короткие периоды считаются по сырым точкам, длинные — по часовой свёртке, которую синхронизация пересобирает в той же транзакции. Пересчёт идемпотентен: свёртку всегда собираю из сырых строк, а не через `+=`. Я замерил: год по дням на лету — 179 мс, через свёртку — 10. С синхронным драйвером эти 179 мс блокировали бы весь сервер. Min и max — реальные наблюдённые цены через bare columns, avg — статистика в double с округлением, и я могу показать, почему погрешность ниже округления».
