# 0002. Модель доступа: API key со scope + BFF в web

- **Статус:** Accepted (06.10.2026)
- **Дата:** 06.10.2026
- **Вопрос брифа:** Q2
- **Требования:** F1, C4, C7, C10
- **Связано:** [0001 — фреймворк web](0001-web-framework.md)

## Контекст

- ТЗ (F1): «Аутентификация и авторизация запросов к собственному API через **Bearer token (API Key)**». Формат задан прямо.
- Курс, урок «Авторизация»: «Даже в учебном проекте нужно разделять, кто просто смотрит данные, а кто может их менять». Там же — принцип наименьших привилегий.
- В брифе две роли: **Viewer** (чтение) и **Operator** (CRUD монет, ручной запуск синхронизации, алерты).
- C7: в `apps/api` нет `jsonwebtoken`, `passport`, `bcrypt`. Есть `node:crypto`.
- Web — это браузер. Ключ, отданный в браузер, считается скомпрометированным: его достаёт любой XSS ([OWASP HTML5 Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)).

## Варианты

1. **Один статический API key из env.** Минимум по ТЗ.
2. **API keys со scope в БД** (`read`, `write`). Ключи хранятся в виде хэша, их можно выпускать и отзывать.
3. **Пользователи + JWT в `apps/api`**: логин/пароль, access/refresh-токены.
4. **BFF в web** поверх варианта 2: пользователи логинятся в web, сессия в httpOnly-cookie. Сервер web ходит в api со своим ключом, scope ключа соответствует роли пользователя.

## Сравнение

| Критерий | 1. Один ключ | 2. Ключи + scope | 3. Users + JWT в api | 4. = 2 + BFF в web |
|---|---|---|---|---|
| Буквально по F1 («Bearer API Key») | ✅ | ✅ | 🟡 Bearer есть, но это не API key | ✅ api по-прежнему на ключах |
| Разделение «смотрит / меняет» (курс) | ❌ | ✅ | ✅ | ✅ |
| Отзыв доступа | ❌ только перезапуск со сменой env | ✅ `revoked_at` | 🟡 JWT нельзя отозвать до истечения | ✅ |
| Влезает в C7 (только `node:crypto`) | ✅ | ✅ | 🟡 подпись JWT пришлось бы писать вручную — это «своя криптография», красный флаг | ✅ |
| Объём кода и тестов в api | минимум | + таблица, CLI, проверка scope | + пользователи, пароли, refresh, ротация | как 2 |
| Ключ не попадает в браузер | — | — | — | ✅ ([RFC 10017](https://www.ietf.org/ietf-ftp/rfc/rfc10017.txt), BCP 212: BFF — самый безопасный паттерн для браузерных приложений) |
| SSE в браузере | — | — | — | ✅ cookie вместо заголовка |

Рынок и стандарты:
- **OWASP API Security Top 10 2023, API2 Broken Authentication** — второй по частоте риск API: слабая аутентификация и отсутствие отзыва ([apisecurity.io](https://apisecurity.io/owasp-api-security-top-10/api2-2023-broken-authentication/)).
- **RFC 10017 (BCP 212, август 2026)**, «OAuth 2.0 for Browser-Based Applications»: BFF «strongly recommended for business applications». Токены не должны быть доступны JavaScript в браузере.
- Ключи со scope — стандартная практика публичных API: так устроены и сам CoinMarketCap (ключ в заголовке), и GitHub fine-grained tokens, и Stripe restricted keys.

## Решение (рекомендация)

**Вариант 4: в `apps/api` — API keys со scope, в `apps/web` — BFF с cookie-сессией.**

### `apps/api` (строго ТЗ)

| Аспект | Решение |
|---|---|
| Заголовок | `Authorization: Bearer <key>` |
| Формат ключа | `cpt_` + 32 случайных байта в base64url (`crypto.randomBytes`). Префикс помогает secret-сканерам и людям опознать ключ |
| Хранение | Таблица `api_keys`: `id`, `name`, `key_prefix` (первые символы — для поиска и логов), `key_hash` (SHA-256), `scopes`, `created_at`, `last_used_at`, `revoked_at`. Сам ключ показываем **один раз** при выпуске |
| Почему SHA-256, а не bcrypt/scrypt | Ключ — 256 бит случайности, перебирать его бессмысленно. Медленный хэш нужен для паролей с низкой энтропией. Так хранят ключи GitHub и Stripe |
| Сравнение | Поиск по `key_prefix`, затем `crypto.timingSafeEqual` по хэшу — защита от timing-атак |
| Scopes | `prices:read` (монеты, цены, история), `watchlist:write` (CRUD монет), `ops:write` (ручная синхронизация, алерты, если будут в api) |
| Ошибки | Нет ключа или ключ неверный → **401** + `WWW-Authenticate: Bearer`. Не хватает scope → **403** с `error="insufficient_scope"` (RFC 6750) |
| Выпуск ключей | CLI `npm run keys:create -- --name web-operator --scopes ...` и `keys:revoke`. Для `docker compose up` — bootstrap: если в env заданы `BOOTSTRAP_*_KEY`, при старте идемпотентно записываем их хэши. Так всё запускается одной командой |
| Публичные эндпоинты | `/status` (liveness/readiness), `/docs` |
| В Express ↔ Nest | `requireAuth()` + `requireScope('watchlist:write')` — middleware на роутере. Аналог `AuthGuard` + `@Scopes()` с `Reflector` в Nest |

### `apps/web` (бонус, библиотеки свободны)

- Пользователи логинятся в web. Сессия — **httpOnly + Secure + SameSite=Lax** cookie.
- Роль пользователя определяет, каким ключом сервер Next ходит в api: Viewer → ключ с `prices:read`, Operator → ключ со всеми scope.
- Браузер не знает ни ключей, ни адреса api.
- Хранилище пользователей web и библиотека сессий — решим в фазе C (вариант по умолчанию: два демо-пользователя из env с хэшем пароля, iron-session).

### Отвергнуто

- **Вариант 1** — нет разделения прав и отзыва. Курс прямо просит разделять чтение и запись.
- **Вариант 3** — уходит от буквы F1, раздувает api на день работы и требует писать JWT руками без библиотеки. Это противоречит и C7, и здравому смыслу. Место для него — `platform` (например, OIDC-провайдер перед api) как «путь миграции».

## Последствия

- ➕ F1 выполнен буквально, плюс есть least privilege и отзыв ключей. Это хороший материал для интервью.
- ➕ Ключи — это данные в БД, а не в памяти (C2 соблюдён).
- ➖ Чуть больше кода: таблица `api_keys`, CLI, middleware scope, тесты (на каждый защищённый эндпоинт: 401 без ключа, 403 без scope, 2xx с правильным ключом — заодно закрывает негативные кейсы C8).
- ➖ Web зависит от bootstrap-ключей в env. Описываем в README и `.env.example`.
- Не делаем: rate limit на неудачные попытки. Записать в бэклог фазы E.

## Как защищать на интервью

«ТЗ требует Bearer API key — я его и сделал, но с двумя ролями через scope, как советует урок про наименьшие привилегии. Ключи храню как SHA-256: у них высокая энтропия, bcrypt тут не нужен. Сравниваю через `timingSafeEqual`. JWT в api не взял: он не по ТЗ, а без библиотеки это своя криптография. Браузер ключа не видит — между ним и api стоит BFF, как рекомендует RFC 10017».
