# 0017. Web: данные для UI, которых нет в контракте (расписание синхронизации, пауза монеты)

- **Статус:** Accepted (11.10.2026) — варианты 1D и 2B
- **Дата:** 08.10.2026
- **Фаза:** C (дизайн `apps/web`), найдено при анализе — [01-reference-analysis.md](../project/design/01-reference-analysis.md#5-влияние-на-adr)
- **Связано:** [0014 — контракт API](0014-api-contract.md), [0015 — планировщик](0015-ports-events-and-lifecycle.md), [0012 — web](0012-web-charts-and-ui-kit.md), [ui-flows.md](../project/ui-flows.md), бриф §2 (правило о ТЗ-эндпоинтах)

## Контекст

При сверке макетов с контрактом нашлись два места, где [ui-flows.md](../project/ui-flows.md) обещает то, чего API не отдаёт.

### Пробел 1. Расписание синхронизации

| Где в ui-flows | Что нужно показать | Что есть в контракте |
|---|---|---|
| §3.2 Дашборд | «Последняя синхронизация: 14:00:03 · успешно · **следующая ≈ 14:05**» | `lastSync` (`id`, `status`, `finishedAt`) — следующего запуска нет |
| §3.6 Синхронизация | карточка «Сейчас»: **следующий запуск** | `listSyncRuns` — только прошлые запуски |
| §3.7 Система | **прогноз**: «при текущем интервале и N монетах квоты хватит до …» | `quota` есть, интервала нет |

Интервал живёт в конфиге api (`SYNC_INTERVAL_MS`, по умолчанию 300 000, минимум 180 000 — [ADR 0015](0015-ports-events-and-lifecycle.md), `apps/api/src/config.ts`). Планировщик — цепочка `setTimeout`: следующий запуск планируется **после завершения** текущего. Значит, `nextRunAt ≈ finishedAt + interval`, но это знает только сам планировщик. `/health/ready` отдаёт лишь `scheduler: running | stopped | disabled`.

### Пробел 2. Пауза монеты на дашборде

- `PATCH isPaused` останавливает синхронизацию монеты ([ADR 0013](0013-data-model.md)). Через два интервала её цена станет `isStale = true`.
- `LatestPriceListItem` (`listLatestPrices`) — это `cryptocurrencyId`, `symbol`, `name`, `latest`. **Признака паузы нет.**
- Итог: дашборд не отличит «оператор поставил монету на паузу» от «CMC лежит». Баннер деградации загорится из-за штатного действия оператора. Это прямое нарушение принципа «честность данных».
- Попадают ли монеты на паузе в `listLatestPrices`, контракт явно не говорит. Реализация (B11) их не отфильтровывает: монета на паузе остаётся в списке и со временем получает `isStale = true`.

### Ограничение брифа

`listLatestPrices` — ТЗ-эндпоинт (тег Prices, F3–F5). Бриф §2: «поведение и контракт ТЗ-эндпоинтов не меняются». `getCmcStatus` — расширение (тег Operations), его менять можно по правилам расширений.

## Варианты

### Пробел 1: расписание

| Критерий | 1A. Убрать из UI | 1B. Интервал в env web | 1C. Вывести из истории запусков | **1D. Блок `schedule` в `getCmcStatus`** |
|---|---|---|---|---|
| Меняет контракт api | ❌ нет | ❌ нет | ❌ нет | 🟡 да, аддитивно, только расширение |
| Точность | — | 🟡 рассинхрон, если env api и web разъедутся | ❌ эвристика: ручной запуск, рестарт и долгий ретрай её ломают | ✅ знает сам планировщик |
| Прогноз квоты (§3.7) | ❌ пропадает | 🟡 | 🟡 | ✅ |
| Состояние «планировщик остановлен» | ❌ | ❌ | ❌ | ✅ `state` |
| Объём | ✅ 0 | ✅ 1 переменная | 🟡 ~40 строк логики с крайними случаями | 🟡 3 поля в схеме + тесты (позитивный и негативный уже есть у операции) |
| Защищаемость | 🟡 «а когда следующая?» | ❌ «два источника правды» | ❌ «угадываете?» | ✅ «спросил у того, кто знает» |

### Пробел 2: пауза

| Критерий | 2A. `isPaused` в `LatestPriceListItem` | **2B. Дашборд читает ещё `listCryptocurrencies`** | 2C. Не отдавать паузу в `/prices` | 2D. Ничего не делать |
|---|---|---|---|---|
| Соблюдает бриф (ТЗ-эндпоинты не меняются) | ❌ меняет контракт ТЗ-эндпоинта | ✅ | ❌ меняет поведение ТЗ-эндпоинта | ✅ |
| Честный баннер | ✅ | ✅ | 🟡 монета исчезает с дашборда | ❌ ложная тревога |
| Запросов на дашборд | 2 | **3** (`listCryptocurrencies` кэшируется и инвалидируется только по `watchlist.changed`) | 2 | 2 |
| Изменения в api | схема + тесты | нет | хендлер + тесты | нет |

`listCryptocurrencies` уже отдаёт `isPaused` и `latestPrice` (Viewer имеет к нему доступ: scope `prices:read`). Третий запрос дешёвый: watchlist ≤ 100 монет, меняется редко, а событие `watchlist.changed` уже инвалидирует кэш.

## Решение

1. **Пробел 1 → вариант 1D.** В `CmcStatus` добавляется обязательный блок `schedule`:

   ```yaml
   schedule:
     type: object
     additionalProperties: false
     required: [state, intervalMs, nextRunAt]
     properties:
       state: { type: string, enum: [running, stopped, disabled] }   # то же, что в /health/ready
       intervalMs: { type: integer, minimum: 180000 }
       nextRunAt:
         type: string
         nullable: true          # null: идёт запуск, планировщик остановлен или выключен
         allOf: [{ $ref: '#/components/schemas/Timestamp' }]
   ```

   - Операция — расширение (`ops:read`), поэтому правило брифа о ТЗ-эндпоинтах не затронуто.
   - **Дашборд Viewer** «следующую синхронизацию» **не показывает**: `getCmcStatus` ему недоступен, и это нормально. Viewer видит последнюю синхронизацию и свежесть. Строка «следующая ≈ …» из ui-flows §3.2 остаётся только у Operator.
   - Оформляется поправкой к [ADR 0014](0014-api-contract.md) по spec-first циклу: спека → тесты → код. Правка делается после сдачи отдельной веткой `feat/api-sync-schedule`: версия `v1.0-submission` не меняется. Пока ветка не влита, `apps/web` «следующий запуск» и прогноз квоты не показывает.

2. **Пробел 2 → вариант 2B.** Дашборд делает **три** запроса: `listLatestPrices` + `listSparklines` + `listCryptocurrencies`.
   - Баннер деградации учитывает только монеты с `isPaused = false`.
   - У монеты на паузе — нейтральная метка «пауза» без ⚠.
   - ui-flows §3.2 («два запроса на весь дашборд») уточняется до трёх.

### Реализация (12.10.2026)

Вариант 1D реализован в ветке `feat/api-sync-schedule` — [поправка от 12.10 к ADR 0014](0014-api-contract.md#поправка-от-1210), версия контракта `1.1.0`. До вливания ветки `apps/web` в `main` работает на контракте `1.0.0`: «следующий запуск» и прогноз квоты не показываются.

## Последствия

- ➕ UI не обещает того, чего нет в данных. Баннер деградации не срабатывает на штатное действие оператора.
- ➕ Правило брифа соблюдено: ТЗ-эндпоинты не тронуты, расширяется только операционный эндпоинт.
- ➕ Тема для интервью: «один источник правды для расписания» и «почему не эвристика по истории».
- ➖ `getCmcStatus` теперь отвечает не только про CMC, но и про планировщик. Имя операции становится чуть уже содержания. Альтернатива — отдельная операция `getSyncSchedule`, но это +1 операция и +2 теста C8 ради трёх полей.
- ➖ Третий запрос на дашборде. Он кэшируется, поэтому на практике это один лишний запрос при открытии страницы.
- Вариант 1A отклонён: «следующий запуск» и прогноз квоты остаются в UI у Operator (см. [README дизайна](../project/design/README.md#принятые-решения), Q2).

## Найдено при реализации C5 (12.10.2026)

- **Web работает с обеими версиями контракта.** Блок `schedule` читается из ответа с проверкой формы ([`readSchedule`](../../apps/web/src/lib/operator/system.ts)); на контракте `1.0.0` расписание и прогноз не показываются. Проверено на локальном стенде с api из обеих веток (`main` и `feat/api-sync-schedule`): «Следующий запуск ≈ …», «Расписание: каждые 3 мин» и прогноз квоты появляются только с api из `feat/api-sync-schedule`.
- **Пробел 3 (открыт): число точек истории монеты.** Макет диалога удаления показывает «будет удалено N точек». `Cryptocurrency` такого поля не отдаёт; посчитать на клиенте можно только перелистав всю историю страницами. Диалог обходится без числа. Варианты для отдельного решения: поле `pricePointsCount` в `Cryptocurrency` (COUNT по индексу на каждую монету списка) или только в `getCryptocurrency`.

## Как защищать на интервью

«Макеты я сверял с контрактом построчно и нашёл два пробела. Первый: UI обещал „следующая синхронизация через…“, а интервал знает только планировщик api. Дублировать его в env web — это два источника правды, угадывать по истории — эвристика. Поэтому три поля в операционном эндпоинте. Второй: пауза монеты через два интервала выглядела бы как падение CMC. Менять ТЗ-эндпоинт `/prices` я не стал — бриф это запрещает. Дашборд просто читает ещё список монет, который и так кэшируется и инвалидируется по SSE».
