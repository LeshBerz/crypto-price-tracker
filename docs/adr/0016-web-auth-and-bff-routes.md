# 0016. Web: пользователи, серверные сессии и маршруты BFF

- **Статус:** Accepted (06.10.2026) — вариант 3 выбран при ревью первой редакции (iron-session)
- **Дата:** 06.10.2026
- **Фаза A:** часть артефакта «UI-флоу» ([ui-flows.md](../project/ui-flows.md))
- **Связано:** [0001](0001-web-framework.md) (Next.js как BFF), [0002](0002-access-model.md) (BFF и ключи; хранилище пользователей отложено до этого ADR), [0003](0003-sqlite-driver-and-node-version.md) (`node:sqlite`), бриф (Viewer входит по логину)
- **DDL (проверен):** [`schema/web_0001_auth.sql`](../project/schema/web_0001_auth.sql)

## Контекст

ADR 0002 решил: браузер не видит ключей api. Пользователь входит в web, сессия живёт в httpOnly-cookie, сервер Next ходит в api ключом по роли. Не решены три вопроса:
1. где хранятся пользователи;
2. как устроена сессия;
3. как BFF защищает свои маршруты.

Web — бонус (C7 не действует), но решение должно защищаться на интервью построчно.

### Проверено руками

| Проверка | Результат |
|---|---|
| SSE через Route Handler Next.js 16.4 (`new Response(upstream.body)`) | ✅ события приходят инкрементально, без буферизации. Ключ подставляется на сервере. Отключение клиента закрывает upstream (`signal: req.signal`) |
| DDL пользователей и сессий на `node:sqlite` | ✅ 7 проверок: невалидный логин, роль, пароль в открытом виде, отзыв без причины — отклоняются. После выхода сессия не находится. Удаление пользователя удаляет его сессии |
| scrypt N=2^17, r=8, p=1 (минимум OWASP Password Storage) | **285 мс на хэш** → только асинхронный `crypto.scrypt` (пул потоков libuv). `scryptSync` блокировал бы Event Loop на каждом входе |

|---|---|---|---|

| Отключить пользователя, «выйти везде», список сессий | ❌ | ✅ | ✅ |
| Аудит: последний вход, неудачные попытки | ❌ | 🟡 | ✅ |
| Управление пользователями без правки env | ❌ | ✅ | ✅ экран оператора |
| Объём | ✅ ~150 строк | 🟡 конфиг + адаптер БД + схема библиотеки | 🟡 ~300 строк + 2 миграции + тесты |
| Защищаемость каждой строки | ✅ | 🟡 «магия» библиотеки | ✅ тот же паттерн, что у ключей api (ADR 0002) |
| Рынок | iron-session 9.0, ~3,1 млн/нед | с 22.09.2025 Auth.js поддерживает команда Better Auth, для новых проектов рекомендуют Better Auth ([анонс](https://www.better-auth.com/blog/authjs-joins-better-auth)) | — |

Почему не библиотека: в проекте вход по паролю для двух ролей, без OAuth и 2FA. Своя реализация по [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) — это ~300 строк, и каждую можно объяснить. В продукте с OAuth/2FA/passkeys правильным ответом был бы Better Auth.

## Решение

**Вариант 3: пользователи и сессии в собственной SQLite web, своя реализация по OWASP.**

### Где живут данные

- **Отдельная БД `web.db`** (`node:sqlite`, raw SQL, миграции как в ADR 0013), а **не** `apps/api`.
- **Почему не в api.** Web отвечает за людей, api — за машинный доступ по ключам. Иначе сдаваемая версия по ТЗ обросла бы пользователями, паролями и сессиями, а это противоречит правилу брифа о расширениях api.
- **В Docker** — свой volume. В `platform` сессии переезжают в Postgres или Redis (тот же порт `SessionStore`).

### Пароли

| Аспект | Решение |
|---|---|
| Алгоритм | `scrypt` (`node:crypto`), N=2^17, r=8, p=1, соль 16 байт. Формат `scrypt$17$8$1$<salt>$<hash>` — параметры в строке, можно усилить позже без миграции |
| Вызов | **только асинхронный** `crypto.scrypt` (285 мс, пул libuv) |
| Сравнение | `crypto.timingSafeEqual` |
| Нет такого логина | всё равно считаем scrypt по фиктивному хэшу: одинаковые время и ответ, логины не перебираются |
| Политика | длина ≥ 12, ≤ 128 символов. Без требований «цифра + спецсимвол» (так рекомендует NIST SP 800-63B) |

### Сессии (OWASP)

| Аспект | Решение |
|---|---|
| Токен | `crypto.randomBytes(32)` → base64url, **256 бит** (OWASP: ≥ 64) |
| Хранение | в БД только **SHA-256 токена**: утечка дампа не даёт рабочих сессий. Как ключи api (ADR 0002) |
| Cookie | `cpt_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` вне `localhost`. С HTTPS — префикс `__Host-` (запрещает подмену с поддоменов) |
| Session fixation | новый токен при каждом входе. Смена пароля или роли → отзыв всех сессий пользователя |
| Таймауты | бездействие **2 ч**, абсолютный **12 ч**. `last_seen_at` продлевается не чаще раза в минуту (меньше записей) |
| Выход | `revoked_at` + `revoke_reason` (`logout`, `logout_all`, `admin`, `password_changed`, `user_disabled`) — для аудита |
| Проверка на запрос | `sessions JOIN users`: не отозвана, не истекла, пользователь активен. Одна выборка по PK |
| Открытый SSE после отзыва | **поток сам не закроется** → BFF перепроверяет сессию на каждом `heartbeat` (25 с) и закрывает поток, если сессия недействительна |
| Очистка | истёкшие сессии удаляются фоновой задачей web раз в час |

### Защита входа

- **Прогрессивная задержка по паре (логин, IP)**: после 5 неудач — ожидание 1 → 2 → 4 … до 15 мин (таблица `login_attempts`, переживает рестарт).
- **Не блокируем аккаунт целиком:** блокировку по известному логину можно использовать как DoS против настоящего пользователя (OWASP Authentication Cheat Sheet).
- Ответ один на все неудачи: «Неверный логин или пароль».

### Пользователи

- **Первый оператор** — из env (`WEB_BOOTSTRAP_LOGIN`, `WEB_BOOTSTRAP_PASSWORD_HASH`), идемпотентно при старте. Пароль в env хранится только как хэш (скрипт `npm run web:hash-password`).
- **Экран «Пользователи и сессии» (Operator):**
  - создать пользователя;
  - сменить роль;
  - отключить (отзывает все его сессии);
  - сбросить пароль;
  - посмотреть активные сессии (время, IP, браузер) и отозвать любую.
- **Свои сессии** в профиле видит каждый пользователь, есть «Выйти на всех устройствах».
- **Защита от потери доступа:** нельзя отключить или понизить последнего активного оператора.

### Маршруты BFF

| Маршрут Next | Роль | Что делает |
|---|---|---|
| `POST /api/session` | — | Вход → новая сессия, cookie |
| `DELETE /api/session` | любая | Выход (отзыв текущей) |
| `GET /api/session` | любая | `{ login, role }` для UI |
| `GET /api/me/sessions`, `DELETE /api/me/sessions` | любая | Свои сессии, «выйти везде» |
| `DELETE /api/me/sessions/[id]`, `PUT /api/me/password` | любая | Завершить одну свою сессию; смена своего пароля (поправка 30) |
| `GET/POST /api/admin/users`, `PATCH /api/admin/users/[id]` | operator | Управление пользователями |
| `POST /api/admin/users/[id]/password-reset` | operator | Сброс пароля: временный пароль в ответе (поправки 29, 30) |
| `GET /api/admin/sessions`, `DELETE /api/admin/sessions/[id]` | operator | Все активные сессии, отзыв. `id` — открытый идентификатор сессии (поправка 27) |
| `GET /api/stream` | любая | SSE-прокси (проверен) + перепроверка сессии на heartbeat |
| `/api/bff/[...path]` | по allowlist | Прокси в `apps/api` |

**Allowlist — статическая таблица** «метод + путь api → минимальная роль», 16 строк по числу операций контракта (ADR 0014):
- `prices:read` → viewer;
- `watchlist:write`, `ops:read`, `ops:write` → operator.

**Тест сверяет таблицу со спекой:** каждая операция есть в таблице, а роль соответствует `x-required-scopes`. Расхождение — красный CI. Чего нет в allowlist — 404.

Ключ api выбирается по роли сессии (viewer-ключ только с `prices:read`). Двойная защита: api сам ответит 403 по scope ключа, даже если BFF ошибётся.

Next.js 16: проверка сессии делается в Route Handlers и серверном layout, а не в `proxy.ts` (бывший `middleware.ts`, [Next 16](https://nextjs.org/blog/next-16)). Proxy годится только для быстрого редиректа неаутентифицированных на `/login` по наличию cookie, без похода в БД.

### CSRF

1. `SameSite=Lax` — cookie не уходит с кросс-сайтовых POST/PATCH/DELETE.
2. Мутирующие маршруты требуют `Content-Type: application/json` — HTML-форма с чужого сайта его не выставит без CORS-preflight.
3. Проверка заголовка `Origin` на совпадение с собственным origin.

### Прочее

- `X-Request-Id`: BFF генерирует его и передаёт в api. Один id в логах web и api.
- Ошибки api (RFC 9457) BFF пробрасывает как есть. UI показывает `title`/`detail` и `requestId`.
- Тесты web (ADR 0009): сервис сессий и паролей — Jest + реальная SQLite `:memory:` (тот же подход, что в api). E2e Playwright: вход, выход, отзыв сессии оператором закрывает SSE у пользователя.

## Последствия

- ➕ Настоящий выход, отзыв, аудит, управление пользователями. Каждый пункт OWASP закрыт осознанно и объясним.
- ➕ Единый паттерн с api: случайный токен + SHA-256 в БД + `timingSafeEqual`.
- ➕ Темы для интервью: session fixation, idle и absolute таймауты, почему хэшировать токен сессии, scrypt и Event Loop, почему не блокировать аккаунт, SSE после отзыва сессии.
- ➖ Web становится stateful: своя БД, миграции, volume, ~300 строк кода с тестами и экран управления пользователями. Это осознанный выбор ради качества.
- ➖ Каждый запрос web — выборка сессии из БД. Для SQLite по PK это микросекунды, а `last_seen_at` троттлится.

| Критерий | Профиль `web` | По умолчанию, запуск без ключей разрешён | По умолчанию, ключи в compose |

### Обновление дашборда и срок бездействия

Запрос через `/api/bff` продлевает срок бездействия (2 ч). Событие `sync.finished` приходит каждые 5 минут и вызывает перезапрос цен — без отдельного решения открытая вкладка не вышла бы по бездействию никогда.

| Критерий | а) Только без таймера | **а + б) Без таймера + признак фона** | в) Открытый дашборд = активность | г) Без перезапросов по событиям |
|---|---|---|---|---|
| Срок бездействия на открытом дашборде | не срабатывает: перезапрос по `sync.finished` чаще раза в 2 ч | срабатывает | не срабатывает | срабатывает |
| Актуальность `isStale`, изменения за 24 ч, мини-графиков | да | да | да | нет — до возврата на вкладку |
| Изменения в коде | нет | заголовок в клиенте, одна проверка в BFF, 3 теста | нет | меньше кода |
| Риск | остаётся только абсолютный срок 12 ч | клиент может солгать заголовком — но только укоротить свою сессию | слабее рекомендаций OWASP по idle timeout | устаревшие данные на экране |

Выбран вариант «а + б». Доверие к заголовку от клиента допустимо, потому что он работает в одну сторону: с признаком сессия не продлевается, без признака — продлевается, как и при любом запросе с действующей cookie. Продлить сессию без запроса признаком нельзя.

Действия пользователя (переход на страницу, возврат на вкладку, кнопка «Повторить») идут без признака и сессию продлевают.

### Идентификатор сессии для маршрутов отзыва

| Критерий | а) Хэш токена как идентификатор | **б) Отдельная колонка `public_id`** | в) Производное значение (хэш от хэша) |
|---|---|---|---|
| Что попадает в браузер | проверочное значение из БД | случайное число, не связанное с токеном | значение, вычислимое из проверочного |
| Изменение схемы | нет | миграция 0002: колонка, заполнение, индекс | нет |
| Поиск сессии | по первичному ключу | по уникальному индексу | перебор сессий пользователя |
| Утечка списка сессий (лог, снимок экрана) | раскрывает содержимое таблицы `sessions` | не раскрывает ничего, кроме факта сессии | почти как «а» |

Выбран вариант «б». Вариант «а» криптографически безопасен (по SHA-256 от 256 случайных бит токен не восстановить), но смешивает две роли: значение, по которому сервер узнаёт токен, становится адресом в URL и попадает в логи запросов.

Отзыв сессии оператором при открытом потоке событий пользователя, стенд в Docker (`api` + `cmc-stub` + `web`): обычный запрос отозванной сессии — 401 сразу; поток получил `session.expired` и закрыт сервером через **25,0 с** (худший случай: heartbeat прошёл перед отзывом); переподключение — 401. ## Как защищать на интервью

«Сессии серверные: в cookie только случайный 256-битный токен, в БД — его SHA-256, поэтому дамп базы не даёт рабочих сессий. При входе токен новый, это защита от fixation. Таймауты двойные: 2 часа бездействия и 12 часов абсолютный. Выход и отключение пользователя действуют сразу. Даже открытый SSE-поток закрывается на ближайшем heartbeat. Пароли — асинхронный scrypt, потому что 285 мс синхронного хэша заблокировали бы Event Loop. Подбор тормозит прогрессивная задержка, а не блокировка аккаунта: блокировку можно использовать как DoS. Пользователи живут в БД web, а не в api: сдаваемый сервис отвечает за машинный доступ по ключам, как требует ТЗ».
