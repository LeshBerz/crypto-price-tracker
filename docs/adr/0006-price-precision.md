# 0006. Хранение и передача цен: точность

- **Статус:** Accepted (06.10.2026)
- **Дата:** 06.10.2026
- **Вопрос брифа:** Q4 (в requirements — открытое решение D4)
- **Требования:** D-2, D-3, правило проекта «деньги и цены не считаются во float без обоснования»
- **Связано:** [0003 — `node:sqlite`](0003-sqlite-driver-and-node-version.md); дальше — Q5 (агрегаты)

## Контекст

Что сервис делает с ценой: хранит историю, показывает, считает min/max/avg и % изменения (Q5), сравнивает с порогом алерта («BTC < 60000»). Деньги никуда не переводятся, балансов нет. Это **рыночные данные**, а не бухгалтерия. Но это финтех, и вопрос «почему цена во float?» на интервью неизбежен.

Особенности данных:
- **Огромный динамический диапазон.** BTC ≈ 1e5 USD, мем-токены ≈ 1e-9 и меньше. Это 15+ порядков.
- **CMC отдаёт цену как JSON number.** Стандартный `JSON.parse` превращает её в double, и точность теряется **до того, как что-то сохранено**.
- **SQLite** знает только INTEGER (int64), REAL (double), TEXT. Типа DECIMAL нет.

### Проверено руками (Node 24.21)

| Эксперимент | Результат |
|---|---|
| `JSON.parse` цены `67123.451234567891` | `67123.4512345679`: последние цифры потеряны |
| `JSON.parse` цены `0.0000000012345678901234` | `1.2345678901234e-9`: экспоненциальная запись |
| `JSON.parse(raw, (k, v, ctx) => ctx.source)` | `"67123.451234567891"`, `"0.0000000012345678901234"`: **ровно то, что прислал CMC** |
| `0.1 + 0.2` | `0.30000000000000004` |
| `MAX(price)` по TEXT-колонке со значениями 9.5, 10.25, 100.1 | `9.5`: **строки сравниваются лексикографически** |
| `ORDER BY price_num` по сгенерированной REAL-колонке | `100.1`: верно |
| CHECK-ограничение из раздела «Схема», 12 значений | принимает `67123.451234567891`, `0.0000000012345678901`, `100`; отклоняет `1.2e-9`, `-5`, `0`, `0.000`, `1.2.3`, `abc`, `12.`, `.5`, `" 1"` |

Reviver с `context.source` — часть предложения TC39 «JSON.parse source text access». Оно достигло Stage 4 (ES2025) и есть в Node 22+ ([tc39](https://tc39.es/proposal-json-parse-with-source/)). Библиотеки не нужны, C7 соблюдён.

## Варианты

1. **REAL (double)** везде.
2. **TEXT** с десятичной строкой.
3. **INTEGER, единый масштаб** (например, цена × 10¹²).
4. **INTEGER, масштаб на монету**, как tick size на биржах.
5. **Две INTEGER-колонки**: мантисса + экспонента (аналог `NUMERIC` в Postgres).
6. **Гибрид: TEXT — точное значение (источник истины) + сгенерированная REAL-колонка** для сортировки, поиска экстремумов и графиков.

## Сравнение

| Критерий | 1. REAL | 2. TEXT | 3. INT единый | 4. INT на монету | 5. Мантисса + эксп. | 6. TEXT + gen. REAL |
|---|---|---|---|---|---|---|
| Точно хранит то, что прислал CMC | ❌ | ✅ | ❌ округление до масштаба | 🟡 масштаб надо угадать | ✅ | ✅ |
| Диапазон 1e-15 … 1e7 | ✅ | ✅ | ❌ int64 при 10¹²: максимум 9,2·10⁶ USD, а цены < 1e-12 становятся 0 | 🟡 если цена сменит порядок, масштаб «съедет» | ✅ | ✅ |
| Сортировка и MIN/MAX в SQL | ✅ | ❌ лексикографически | ✅ | ❌ разные масштабы несравнимы | ❌ нужна нормализация | ✅ по REAL-колонке, а отдаём точный TEXT найденной строки |
| AVG/SUM в SQL | 🟡 с ошибкой float | ❌ | ✅ (до переполнения) | ❌ | ❌ | 🟡 float, только для статистики (Q5) |
| Простота схемы и кода | ✅ | ✅ | 🟡 | ❌ | ❌ | ✅ одна колонка пишется, вторая вычисляется СУБД |
| Защищаемость в финтехе | ❌ «цены во float» | 🟡 «а как сортируете?» | 🟡 «а мем-коины?» | ✅ так делают биржи, но tick size от CMC нет | ✅, но сложно | ✅ |

### Практика рынка

- **Биржевые API отдают цены строками**: Binance (`"price": "4.00000100"`), Coinbase, Kraken. Причина — JSON-парсеры молча превращают числа в double ([пояснение Alpaca](https://forum.alpaca.markets/t/why-are-some-json-response-values-strings-instead-of-numbers/6059)).
- **Биржи внутри хранят цены как целые в единицах tick size инструмента** (вариант 4). У CMC tick size нет: это агрегатор.
- **Postgres `NUMERIC`** — эталонный DECIMAL. Это кандидат для `platform` (Q8).

## Решение (рекомендация)

**Вариант 6. Точное десятичное значение хранится как TEXT и путешествует строкой от CMC до клиента. Float используется только там, где он безопасен и явно назван.**

### 1. Приём от CMC

Axios-клиент CMC парсит ответ своим `transformResponse`: `JSON.parse` с reviver. Для полей `price` берём `ctx.source` — исходный текст числа, без промежуточного double. Затем строку нормализуем через `Decimal.parse`:
- экспоненту разворачиваем (`1.2e-9` → `0.0000000012`);
- хвостовые нули убираем;
- отрицательные, нулевые, `NaN` и строки длиннее 40 символов отклоняем как невалидные данные от CMC: точку логируем, остальной батч сохраняем.

### 2. Схема

```sql
CREATE TABLE price_history (
  id                INTEGER PRIMARY KEY,
  cryptocurrency_id INTEGER NOT NULL REFERENCES cryptocurrencies(id) ON DELETE CASCADE,
  price             TEXT    NOT NULL
                    CHECK (price GLOB '[0-9]*'                   -- начинается с цифры
                       AND price NOT GLOB '*[^0-9.]*'            -- только цифры и точка
                       AND price NOT GLOB '*.*.*'                -- не больше одной точки
                       AND price NOT GLOB '*.'                   -- не заканчивается точкой
                       AND CAST(price AS REAL) > 0),
  price_num         REAL    GENERATED ALWAYS AS (CAST(price AS REAL)) VIRTUAL,
  fetched_at        TEXT    NOT NULL                             -- формат времени — в ADR модели данных
);
```

- `price` — источник истины. CHECK — вторая линия обороны после валидации в коде: БД не примет мусор, даже если код ошибётся.
- `price_num` — производная колонка. Её вычисляет SQLite, приложение её никогда не пишет, рассинхрон невозможен. VIRTUAL — места не занимает.
- Полная схема и индексы — в ADR модели данных (после Q5).

### 3. Арифметика в приложении

Свой маленький value object `Decimal` в `common/decimal.ts`: `bigint`-мантисса + масштаб, около 100 строк, на сто процентов покрыт тестами.
- Операции: `parse`, `toString`, `compare`, `add`, `sub`, `mul`, `div(scale, rounding)`.
- Округление явное: `HALF_EVEN` (банковское), чтобы не накапливать смещение в статистике.
- Где используется: сравнение с порогом алерта, % изменения, avg (если Q5 выберет точный расчёт).

### 4. Контракт API

- Цены в ответах — **JSON string**: `"price": "67123.451234567891"`.
- Валюта — явное поле `"currency": "USD"` (D-3). Единая валюта задаётся конфигом, `convert=USD` в запросах к CMC.
- Входящие цены (пороги алертов) принимаем **только строкой** формата `^\d+(\.\d+)?$`. Число в JSON → 400. Так клиент тоже не потеряет точность по дороге.
- Вычисленные значения (avg, % изменения) — тоже строки, с зафиксированной в контракте точностью (Q5).

### Где float допустим и почему

| Место | Почему безопасно |
|---|---|
| `price_num` для `ORDER BY`, `MIN/MAX`, `WHERE price_num < ?` | Нужен только **порядок** значений. Double различает значения с точностью до ~15 значащих цифр, а отдаётся точный `price` найденной строки |
| Графики в web | Пиксель на экране грубее double |

## Последствия

- ➕ Сквозная точность: от байтов CMC до JSON клиента ни одна цифра не теряется. Это можно показать тестом.
- ➕ Стандартный стиль финтех-API (строки) и сильный интервью-кейс: `context.source`, лексикографическая ловушка TEXT, почему не int64-масштаб.
- ➖ Свой `Decimal`: ~100 строк кода и тщательные тесты (граничные: `0.1 + 0.2`, огромные и крошечные значения, округление `.5`).
- ➖ Клиенты должны работать со строками. Для web это нормально: форматирование через `Intl.NumberFormat` принимает строку.
- ⚠️ **Риск:** формат реального ответа CMC (number, а не string; наличие экспоненты) проверяем на первом же запросе с ключом в фазе B. Если CMC пришлёт строку, reviver тривиально упрощается.
- `platform` (Q8): в Postgres колонка `NUMERIC`, контракт API не меняется.

## Как защищать на интервью

«Цены храню как точную десятичную строку, а рядом генерируемая REAL-колонка — только для сортировки и поиска экстремумов. Точность теряется не в БД, а уже в `JSON.parse`, поэтому ответ CMC разбираю reviver'ом с `context.source` и забираю исходный текст числа. Int64 с фиксированным масштабом не подходит: диапазон цен в крипте — 15 порядков, мем-коины обнулились бы. Арифметику делаю в своём `Decimal` на BigInt с банковским округлением. Клиенту отдаю строки, как Binance и Coinbase».
